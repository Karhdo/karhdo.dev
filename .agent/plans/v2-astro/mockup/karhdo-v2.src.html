How to Prevent Overbooking in SQL with Multiple Methods

Do Trong Khanh·Mar 19, 2025·8 min read·1,284 views (sample)

Introduction

In any application involving booking hotel rooms, flight seats, or similar resources, data integrity is crucial to ensure multiple users can't "claim" the same slot concurrently. We need an effective way to handle concurrency so that two customers booking at nearly the same time don't exceed the actual available count.

This post covers the popular techniques in SQL:

  1. Pessimistic Lock using SELECT ... FOR UPDATE.
  2. Optimistic Lock using a version (or timestamp) column.
  3. Transaction Isolation Level, especially SERIALIZABLE.
  4. Advanced solutions, such as distributed locks and caching.

Pessimistic Lock: SELECT ... FOR UPDATE

Pessimistic lock assumes conflicts are likely, so it locks rows before updating to stop other transactions from interfering.

book-room.sqlsql
START TRANSACTION;-- Lock the row and read dataSELECT availableFROM roomsWHERE room_type = 'Deluxe'FOR UPDATE; -- Check if available > 0UPDATE roomsSET available = available - 1WHERE room_type = 'Deluxe';COMMIT;

How it works

  • FOR UPDATE locks the matching rows (row-level locking in InnoDB).
  • Another transaction touching room_type = 'Deluxe' will wait until the first one commits or rolls back.
  • So two transactions can never both read available = 5 and decrement it at the same time.
Tip
For small and medium applications, SELECT ... FOR UPDATE is usually enough: correct, with little overhead.

Optimistic Lock: Using a version Column

By contrast, optimistic lock assumes conflicts are rare and doesn't lock rows on read. It checks for conflicts at update time using a version column.

optimistic.tsts
const result = await db.update(rooms)  .set({ available: sql`available - 1`, version: room.version + 1 })  .where(and(eq(rooms.id, room.id), eq(rooms.version, room.version))); if (result.rowCount === 0) throw new ConflictError('Room was just booked, retry');

Using SERIALIZABLE

The strictest isolation level makes concurrent transactions behave as if they ran one after another, at the cost of more retries under load.

Advanced Solutions

Distributed locks (Redis, Redlock), queues and caching help when a single database becomes the bottleneck.

Conclusion: Which Method to Choose?

Start with pessimistic locking, reach for optimistic locking when contention is low and reads dominate, and use SERIALIZABLE or distributed locks only when you need them.
